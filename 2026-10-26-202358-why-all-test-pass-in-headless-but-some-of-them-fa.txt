  Why headed behaves differently

  1. Your real mouse and the OS window get in the way.
  In headed mode each test opens a real window on your desktop. If your cursor
  is over one of those windows, or a window opens under it, Windows sends real
  mouse events. Those cancel Playwright's simulated hover. Tests at risk:
  - additional-scenarios-2.spec.ts:16-27: the jQuery UI menu uses nested
    .hover() calls, and the submenu closes when the mouse "leaves".
  - interactions.spec.ts:42-54: the Hovers test.
  - tables-status-misc.spec.ts:180-181: Exit Intent. Calling mouse.move(0, -100)
    to leave the page works headless, but in a real window the mouseleave event
    often doesn't fire the same way.

  2. Focus.
  Headless, every page acts as if it has focus. Headed, only one window on your
  desktop really has OS focus, and with fullyParallel: true you have several
  open at once. This affects:
  - Control+A in TinyMCE (additional-scenarios-2.spec.ts:134)
  - blur() followed by keyboard.press('Enter') (interactions.spec.ts:153)
  - the right-click context menu (interactions.spec.ts:123)

  3. Timing.
  Headed browsers are slower because they actually draw the page. Your config
  also uses the default worker count (about half your CPU cores) across 3
  browsers, so many real windows compete for CPU. Fixed waits like
  waitForTimeout(2000) for TinyMCE, infinite scroll and geolocation
  (additional-scenarios-2.spec.ts:77,107,123, advanced.spec.ts:41,51,112) are
  then sometimes too short, especially against the slow herokuapp site.

  4. Windows display scaling.
  If your display is set to 125% or 150%, a real window can map coordinates
  slightly differently. This can break dragTo and hover.

  How to confirm and fix

  1. Run headed with one worker, and don't touch the mouse while it runs:
  npx playwright test --headed --workers=1 --project=chromium
     If most failures go away, the cause is CPU load or focus.
  2. Replace waitForTimeout(...) with assertions that wait for something
     specific, e.g. await expect(iframe.locator('body#tinymce')).toBeVisible()
     or await expect(locator).toHaveCount(n).
  3. For Exit Intent, dispatch the event yourself instead of relying on real
     mouse movement:
  await page.dispatchEvent('html', 'mouseleave', { clientY: -10 });
  4. For hover menus, check that each submenu is visible before moving to the
     next level. Your tests already do this.

  Unrelated, but it will fail in both modes on Windows:
  additional-scenarios-1.spec.ts:63 saves the download to /tmp. Use os.tmpdir()
  or testInfo.outputPath() instead.

  What was wrong

  When I ran headed, every failure was in Firefox. Which tests failed changed
  from run to run, so the test logic wasn't the problem. My earlier guesses
  about the mouse and focus were wrong; there were two problems with how Firefox
  runs headed on Windows, plus one test that was flaky in both modes.

  1. Clicks hung forever (most failures).
  Playwright runs tests in parallel, so several Firefox windows were open on top
  of each other. Windows tells Firefox when a window is fully covered, and
  Firefox then stops drawing it to save resources. In Firefox, a Playwright
  click waits for the next drawn frame, so in a covered window the click never
  finished and the test timed out at 30s. Headless has no real windows, so
  nothing gets covered.

  Fix (playwright.config.ts, Firefox project): turn off that Firefox setting.
  launchOptions: {
    firefoxUserPrefs: { 'widget.windows.window_occlusion_tracking.enabled':
  false },
  },
  This took the Firefox-only headed run from 9 failures to 3.

  2. "Tearing down context exceeded the test timeout" (the remaining failures).
  Simple tests like Shadow DOM passed, then hung while the browser closed. Your
  config records video for every test (video: 'retain-on-failure'), and on close
  Playwright waits for the video to finish. Headed Firefox's video recording
  sometimes stalls, so closing never completed. With video off, all 69 Firefox
  tests passed headed.

  Fix: turn video off only for headed Firefox. Headless and the other browsers
  still record video.
  if (process.argv.includes('--headed')) process.env.PW_HEADED = '1';
  const headed = process.env.PW_HEADED === '1';
  ...
  video: headed ? 'off' : 'retain-on-failure',
  The env var is needed because Playwright's worker processes reload the config
  without the --headed flag, but they do inherit environment variables.

  3. Infinite Scroll was flaky in both modes.
  It scrolled down and then waited a fixed 2 seconds for new content from the
  slow herokuapp site. It failed once headed (Firefox) and once headless
  (Chromium) during my runs. Fix (tests/advanced.spec.ts): instead of the fixed
  wait, it keeps scrolling and checking the paragraph count with expect.poll (up
  to 15s) until the count goes up. It passed 24 repeated runs across headed and
  headless.

  Limits

  - Headed Firefox no longer records failure videos. Screenshots and traces
    still work.
  - Other tests still use fixed waitForTimeout waits (TinyMCE, geolocation).
    They passed in every run, but they could become flaky on a slower machine or
    network.
